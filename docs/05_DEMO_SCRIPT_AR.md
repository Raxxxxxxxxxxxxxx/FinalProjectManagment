# سيناريو العرض أمام لجنة المناقشة

## 1. الهدف

عرض القيمة الأساسية للنظام خلال 10–12 دقيقة: تعدد الأدوار، مقارنة عرضين،
سلامة اختيار الفائز، بوابة الدفع، انتقالات التنفيذ، الأثر الزمني، التعريب
والصلاحيات. لا يحاول السيناريو استعراض كل شاشة.

## 2. حسابات العرض

كلمة المرور في بيانات العرض فقط: `Demo12345!`

| الدور | الحساب | استخدامه في السيناريو |
|---|---|---|
| صاحب مشروع | `owner_demo` | المقارنة والاختيار والدفع والاستلام والتقييم |
| المورد الأول | `supplier_demo` | عرض أسرع، ثم إشعار عدم الاختيار |
| المورد الثاني | `supplier2_demo` | عرض أقل سعراً، ثم تنفيذ أمر الشراء |
| الإدارة | `admin_demo` | مراجعة التحويل والتقرير العام |

> هذه حسابات معروفة عمداً لبيئة demo. لا تستخدم في نشر عام أو إنتاجي.

## 3. تجهيز البيئة قبل المناقشة

نفذ قبل العرض، وليس أمام اللجنة:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
npm install
npm run css:build
python manage.py migrate
python manage.py seed_demo --reset
python manage.py check
python manage.py test
python manage.py runserver
```

افتح `http://127.0.0.1:8000`.

### فحص سريع

- الصفحة الرئيسية تعمل بالعربية.
- تبديل الإنجليزية يعرض `dir="ltr"`.
- الوضع الداكن والفاتح يعملان.
- الحسابات الأربعة تقبل الدخول.
- طلب «تجهيز مكاتب الفرع الجديد» Open وله عرضان Pending.
- لا يوجد أمر شراء مرتبط بهذا الطلب قبل بدء السيناريو.
- الطلب الثاني Shipped مع COD، والثالث Open، والرابع Completed مع تقييم.
- الكتالوج يحوي أربعة عناصر من موردين موثقين.
- `/health/` يعيد `{"status":"ok"}`.
- `static/css/tailwind.css` موجود ولا يظهر `cdn.tailwindcss.com` في الصفحة.

### الحفاظ على نقطة بداية قابلة للاستعادة

قبل كل تدريب نفذ:

```bash
python manage.py seed_demo --reset
```

يحذف الأمر بيانات حسابات demo الأربعة وما يرتبط بها فقط، ثم يعيد بناء
الكتالوج والحالات الأربع. ويرفض التنفيذ تلقائياً عند `DEBUG=False` حتى لا
ينشئ حسابات بكلمة مرور demo ثابتة في بيئة منشورة.

## 4. إعداد قاعة العرض

- متصفح أساسي لصاحب المشروع.
- نافذة خاصة للمورد، ويمكن استخدام نافذة ثالثة للإدارة.
- Zoom المتصفح 90–100% ودقة عرض معروفة.
- تبويبات مفتوحة مسبقاً للصفحة الرئيسية، مخطط المعمارية، ونتيجة الاختبارات.
- نسخة PDF أو صور للشاشات الأساسية كخطة بديلة.
- إيقاف الإشعارات الشخصية والتحديثات التلقائية.
- عدم فتح ملفات البيئة أو كلمات مرور حقيقية على الشاشة.

## 5. النص التنفيذي بالدقائق

### 00:00–00:45 — المشكلة والحل

**الشاشة:** الصفحة الرئيسية.

**النص المقترح:**

> المشكلة ليست في العثور على مورد فقط، بل في توحيد الطلب والعرض والقرار
> والتنفيذ ضمن سجل يمكن الرجوع إليه. المنصة تحول دورة التوريد من مراسلات
> متفرقة إلى workflow تحكمه الصلاحيات والحالات.

أشر إلى المراحل الرئيسية وإحصاءات النظام الفعلية. وضح أن «الوفر التقديري»
محسوب من الفرق بين السعر الفائز ومتوسط عروض الطلبات المتعاقد عليها، وليس
وفراً محاسبياً مدققاً.

### 00:45–01:30 — الهوية والتعريب

1. بدّل الوضع الفاتح/الداكن.
2. بدّل إلى English ثم أعد العربية.
3. صغّر العرض briefly لإظهار قائمة الهاتف إن أمكن.

**النقطة العلمية:** اللغة تديرها Django i18n والاتجاه يحدد من اللغة، بينما
يحفظ المتصفح الثيم محلياً.

### 01:30–02:15 — الثقة والكتالوج

1. افتح كتالوج المنتجات والخدمات.
2. استخدم البحث أو التصنيف.
3. افتح عنصراً ثم ملف المورد.
4. وضح أن الكتالوج العام يعرض منتجات نشطة لموردين موثقين.

**حد صريح:** التوثيق يدوياً من الإدارة، ووثيقة السجل لا تعرض للعامة.

### 02:15–03:00 — منظور صاحب المشروع

1. سجل الدخول `owner_demo`.
2. افتح لوحة التحكم.
3. اذكر أن إنشاء RFQ يفرض موعداً صالحاً وبنداً واحداً على الأقل.
4. افتح طلب «تجهيز مكاتب الفرع الجديد».
5. انتقل إلى مقارنة العروض.

لا حاجة لإنشاء طلب جديد فعلياً؛ يكفي فتح نموذج الإنشاء وشرح validation إن
كان الوقت يسمح.

### 03:00–04:20 — مقارنة عرضين واعتماد واحد

اعرض المقارنة:

| المورد | القيمة | المدة | المفاضلة |
|---|---:|---:|---|
| `supplier_demo` | 4850 USD | 9 أيام | أسرع |
| `supplier2_demo` | 4590 USD | 12 يوماً | أقل سعراً |

1. وضح أن النظام يبرز الأرخص والأسرع لكنه لا يتخذ القرار بدلاً من المالك.
2. اشرح الدرجة: 50% سعر، 30% مدة، 20% تقييم؛ المورد بلا تقييم يأخذ 3/5.
3. أشر إلى أن `supplier2_demo` موصى به تقريباً بدرجة 92.5/100، لكن الزر لا
   ينفذ تلقائياً.
4. اختر عرض `supplier2_demo`.
5. أكد الاختيار.
6. افتح أمر الشراء الناتج.

**النص المقترح:**

> العملية ذرية: يتحول الفائز إلى Selected، المنافس إلى Rejected، الطلب إلى
> Awarded، وتنسخ البنود والسعر والمدة إلى أمر شراء. يوجد قيد قاعدة بيانات
> يمنع فائزاً ثانياً حتى لو تكرر الطلب.

اعرض رقم الأمر وsnapshot البنود وأول حدث في timeline.

### 04:20–05:10 — منظور المورد

1. سجل الخروج أو انتقل إلى نافذة المورد.
2. ادخل `supplier2_demo`.
3. افتح الإشعار أو قائمة الأوامر.
4. افتح الأمر وأكّد قبوله.

**النقطة العلمية:** لا يستطيع مورد آخر فتح الأمر؛ queryset مقيد بالمورد
المختار ويستخدم النظام 404 لتقليل كشف وجود كائن خاص.

### 05:10–06:10 — تسجيل التحويل

1. عد إلى `owner_demo`.
2. افتح الأمر.
3. اختر Bank Transfer.
4. أدخل المرجع: `DEMO-BANK-2026`.
5. أرسل البيانات.

**حد صريح:**

> هذا تسجيل إداري لمرجع التحويل، وليس ربطاً ببنك ولا تخزيناً لبيانات بطاقة.

يمكن ذكر مسار COD كبديل يسمح بالتجهيز بعد الإرسال ويؤكد عند الاستلام.

### 06:10–07:00 — قرار الإدارة

1. انتقل إلى `admin_demo`.
2. افتح إشعار الدفع أو الطلب المعلق.
3. اعرض المبلغ والمرجع.
4. اختر Confirm واكتب «تمت مطابقة المرجع التجريبي».

وضح أن الرفض يتطلب سبباً ويمكن للمالك إعادة الإرسال، وأن صلاحية القرار
تتحقق داخل service لا من زر الواجهة فقط.

### 07:00–08:10 — التنفيذ والشحن

ارجع إلى `supplier2_demo` ونفذ بالترتيب:

1. Confirmed → Preparing، ملاحظة: `بدأ تجهيز الطلب`.
2. Preparing → Shipped، reference: `SHAM-DEFENSE-2026`.
3. Shipped → Delivered، ملاحظة: `تم التسليم إلى موقع المشروع`.

بعد كل خطوة أشر إلى:

- الحالة الجديدة.
- سجل الوقت والممثل والدور والملاحظة.
- الإشعار الموجه للطرف الآخر.
- استحالة القفز فوق مرحلة أو بدء التجهيز قبل تحقق الدفع.

### 08:10–09:00 — الاستلام والتقييم

1. عد إلى `owner_demo`.
2. أكد الاستلام لتحويل Delivered → Completed.
3. افتح التقييم واختر 5/5 مع تعليق مختصر.
4. اعرض وصول تقييم المورد ومتوسطه.

وضح أن الإكمال يغلق RFQ وأن OneToOne يمنع تقييماً ثانياً.

### 09:00–09:45 — التقارير والأثر الزمني

1. افتح صفحة التقارير.
2. اعرض توزيع الحالات والمؤشرات المقيدة بدور المالك.
3. نزّل CSV ووضح أنه لا يحتوي إلا أوامر الدور الحالي وأن قيم الصيغ تحيّد.
4. ارجع إلى أمر الشراء واعرض timeline كاملاً.
5. افتح معاينة الطباعة الرسمية دون طباعتها.

**حد صريح:** التقارير الحالية تشغيلية أساسية؛ لا تحتوي بعد نطاقاً زمنياً أو
PDF محاسبياً، ولا ينبغي جمع عملات مختلفة مستقبلاً دون تحويل.

### 09:45–10:45 — المعمارية والاختبارات

اعرض `docs/02_ARCHITECTURE_AR.md`:

- MVT مع service layer.
- المعاملة الذرية لاختيار العرض.
- ERD وsnapshot البنود.
- خوارزمية قرار شفافة وليست اختياراً آلياً.
- Tailwind محلي وCSP وhealth endpoint.
- SQLite للعرض وPostgreSQL هدف الإنتاج.

ثم اعرض نتيجة **52/52 اختباراً ناجحاً** من تقرير الاختبارات، ولا تشغل
`python manage.py test` كاملاً أثناء العرض إلا إذا طلبت اللجنة ذلك.

### 10:45–11:30 — الأمن والحدود والخاتمة

اذكر بسرعة:

- CSRF، scoping للكائنات، password hashing، constraints.
- وثيقة المنشأة خاصة.
- لا بيانات بطاقة ولا ادعاء بدفع حقيقي.
- CSP وReferrer/Permissions headers وأصول محلية وصفحات أخطاء.
- مستقبل المشروع: PostgreSQL، audit عام، بوابة دفع، بريد/SMS، API ونزاعات.

**الخاتمة المقترحة:**

> القيمة الأساسية للمشروع هي أن كل قرار مهم يتحول إلى حالة وقاعدة وصلاحية
> وأثر قابل للتتبع، وليس مجرد مجموعة صفحات لإدخال البيانات.

## 6. أسئلة متوقعة وإجابات قصيرة

### لماذا Django؟

يوفر auth وCSRF وORM وforms وi18n وadmin ضمن إطار متكامل، ويتيح التركيز على
قواعد التوريد بدل إعادة بناء هذه الأساسات.

### كيف تمنعون اختيار عرضين؟

بمعاملة ذرية وإعادة فحص الحالة مع `select_for_update`، إضافة إلى
UniqueConstraint مشروط يسمح بعرض Selected واحد فقط لكل RFQ.

### لماذا تنسخون البنود؟

لأن RFQ يمثل ما طلب قبل التعاقد، وأمر الشراء يجب أن يحتفظ بنسخة الاتفاق حتى
إن تغيرت بيانات مرجعية لاحقاً.

### هل الدفع حقيقي؟

لا. النسخة الحالية تسجل تحويلاً يدوياً أو COD وتدير الموافقة. الربط الحقيقي
يتطلب مزوداً وwebhooks وأمن وتسويات.

### لماذا SQLite؟

للتطوير والعرض المحلي وبساطة إعادة البيئة. الإنتاج المتزامن يحتاج PostgreSQL
حتى تعمل الأقفال والاعتمادية بمستوى أعلى.

### أين الابتكار؟

التجميع المتكامل لدورة RFQ والمقارنة والاختيار الذري وsnapshot وبوابة الدفع
والأثر الزمني ضمن واجهة عربية ثنائية الاتجاه. كما تنفذ المقارنة درجة شفافة
متعددة المعايير 50/30/20 لتفسير التوصية، لكنها ليست ذكاءً اصطناعياً ولا
تستبدل قرار صاحب المشروع.

| الخلل | التصرف |
|---|---|
| تعذر الإنترنت | أكمل العرض؛ Tailwind وJavaScript والصور محلية |
| تغيرت بيانات الطلب | نفذ `python manage.py seed_demo --reset` قبل العرض |
| تعذر تبديل الحسابات | استخدم نوافذ خاصة مجهزة مسبقاً |
| فشل خطوة workflow بسبب التدريب السابق | افتح الطلب الثاني المتقدم واشرح السجل الموجود |
| تعذر تشغيل الخادم | اعرض فيديو قصيراً وصوراً مع ERD ونتائج الاختبار |
| سؤال خارج النطاق | اربطه صراحة بخارطة الطريق ولا تدّعِ تنفيذه |
